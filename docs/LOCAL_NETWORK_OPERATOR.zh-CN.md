# M11：本机网络操作工具

**只限一台机器上、无价值测试资产的固定四验证者实验。不是主网、匿名网络或生产钱包。**

新增 `zevune-network`：`init`、`run`、`sync`、`submit` 和 `version`。所有会读写账本的命令都要求 `--no-real-funds`。不安装软件、不开放公网、不修改现有数据、不自动重播付款。原根程序 `zevuned` 的数据和行为不变。

## 信任与保存边界

- 初始化从已核验的公开测试创世清单建立新目录，生成各节点自己的签名密钥；不会提供或输出全网查看密钥。清单公开初始地址、金额和 note opening，总量固定 100000 测试单位，仅显式编译 `local-funding-lab` 后可用，无后续任意增发接口。
- 网络配置绑定创世文件、资产清单与公开节点标识。调用者独立保存 `config_sha256`；从同一个不可信提供者同时取得文件和摘要，不构成可信引导。
- `run` 保留签名状态与已有 Orchard 日志；缺失文件会失败，不重置。节点只读取自己的私有文件，其余节点使用公开标识。可选择 `--stop-on-stdin-eof` 供本机进程监督器停止节点，默认使用 Ctrl+C/SIGTERM。共识引擎意外退出时操作进程返回失败，不保持只剩外壳的运行状态。Windows 关机只提供尽力清理机会，不等于断电保证。
- `sync` 仅连接明确的 `http://127.0.0.1:端口`。禁用 DNS、代理、重定向、压缩回包及公网地址，限制响应大小、超时、区块数。此限制是实验的安全边界，不是匿名传输。
- 同步验证真实法定票权签名、链标识、固定验证者集合、参数摘要、区块完整内容及前后链接。每个区块独立执行后，先比较下一份已签名区块头中的 AppHash，再写入参考账本。错误的后置状态不得先落盘后再检查。
- 参考账本高度是已经执行并获下一份区块头绑定的高度；因此同步到观察到的 tip-1。签名并不证明提供者告知的是全网最新 tip；存在数据扣留、隔离和法定票权密钥被攻破等边界。
- `submit` 同步已存在的参考账本，再做真实本地交易检查，最后只广播一次完全相同的签名字节。返回 `accepted_to_mempool_not_confirmed` 且 `confirmed:false`。超时、拒绝或不确定回复都不取消钱包资产预留，不表示付款全网未发生。
- 同步在后续区块失败前可能已经保存较早的正确区块；不回滚这些正确更新。写入确认丢失仍须重开、对账，不能自动重试 Commit。

## 构建与分发

源仓库中的 Go 1.27.1、Rust 1.98.1 和依赖锁需已就绪。根 Go、嵌套 CometBFT、Rust 是不同模块，根目录 `go test ./...` 不覆盖所有模块。

在干净源码目录执行：

```text
python scripts/build_local_lab.py --output <尚不存在的输出目录>
```

脚本先将准确提交的 Git blob 导出到隔离的临时源码目录，再构建 `zevune-network`、`zevune-pool-worker`、`zevune-wallet-local`，复制 Python 钱包控制台与本说明，生成对应准确提交及每个文件 SHA-256 的清单。依赖由固定锁解析，脚本本身不安装编译器；首次依赖下载可能由 Go/Cargo 发起。输出目录必须不存在；失败保留新建的部分目录供检查，不覆盖旧版本。

v2 清单同时记录源码树。独立核验命令与未跟踪源码隔离边界见 [构建完整性](BUILD_INTEGRITY.zh-CN.md)。核验器不会启动程序或修改文件。

清单用于完整性和来源核对，不是签名发布、可复现构建证明或安全审计。分发包不含种子、钱包、验证者密钥、实际签名状态、测试数据目录或 funded-scenario 测试驱动。使用包中的 Python 控制台时显式传 `--backend` 和核验后的 `--backend-sha256`。

## 操作顺序（开发者参考，本轮不要求用户执行）

钱包、节点目录和参考日志应放在版本库之外的个人数据目录。所有路径使用绝对路径，摘要使用独立核对的 64 位小写十六进制字符串；不要把钱包密码放到命令参数或环境变量里。钱包控制台通过隐藏输入取得密码，经本地管道调用 Rust。

1. 用 `scripts/zevune_wallet.py` 创建测试钱包，再以 `init-test-ledger` 创建公开测试清单。该清单不是匿名发行规则。
2. `zevune-network init --no-real-funds --worker <worker> --worker-sha256 <摘要> --home <新目录> --genesis <清单> --genesis-sha256 <清单摘要>`。
3. 保存返回的配置摘要。在四个本机进程分别执行 `run --no-real-funds --worker <worker> --worker-sha256 <摘要> --config <network.json> --config-sha256 <独立保存的摘要> --node <0到3> --base-port 30000`。
4. `sync --no-real-funds --worker <worker> --worker-sha256 <摘要> --config <network.json> --config-sha256 <摘要> --endpoint http://127.0.0.1:30000 --journal <新参考日志> --create`。后续同步同一路径必须去掉 `--create`，绝不将节点正在使用的日志当参考日志。
5. 钱包控制台使用该参考日志检查余额并执行 `prepare`，保存精确签名交易。控制台本身不连接网络、不声称仅凭本地日志已获得共识认证。
6. `submit` 使用与 `sync` 相同配置、参考日志、端点，再加 `--tx <签名交易文件>`，没有 `--create`。
7. 等待后续同步覆盖付款所在区块，再通过钱包 `status` 扫描更新收款/找零。中断或失败先同步对账，使用 `pending` 恢复原交易，不重新签第二笔来替代不确定付款。

文件哈希核验、固定验证者网络证书和钱包密码分别解决不同问题。此工具不提供助记词、多设备安全、长期存储扩容、主网创世隔离、动态验证者、网络匿名或绝对不可追踪保证。
