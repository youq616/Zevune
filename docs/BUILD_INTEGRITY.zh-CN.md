# 本地实验包：源码隔离与完整性核验

本项目仍是单机、固定验证者、无价值测试资产的开发实验。构建成功或文件校验通过，不表示主网可用、匿名性成立、通过审计或获得分发许可。

## 修复的来源标识缺口

旧构建器只检查已跟踪文件是否修改，然后在工作目录内编译。未跟踪或被忽略的额外 Go/Rust 编译输入可能参与构建，但清单仍只显示某个 Git 提交。这会使构建来源说明不完整。

新构建器捕获一个明确提交，以 `git ls-tree` 列举对象，再通过不启用替换对象、textconv 或 checkout 过滤的 `git cat-file --batch` 读取精确 blob 字节。在全新的临时目录中检查对象标识后编译，不把原工作副本的未跟踪源码、忽略目录、临时 Cargo 配置或旧构建产物复制为输入。限制文件数、单文件和总源码字节；拒绝符号链接、子模块、不安全路径和跨平台大小写冲突。记录提交 ID 与源码树 ID。

这不是恶意编译器沙箱，也不是可复现构建证明。Git、编译器、操作系统、依赖缓存和用户构建环境仍是信任前提。Cargo 的依赖 build script 仍会按正常编译流程运行。构建器不自行安装软件，不启动节点；依赖下载仍可能由 Go/Cargo 发起。

## 新清单与核验器

`BUNDLE-MANIFEST.json` 使用 `zevune-local-bundle-2`，包含提交、源码树、编译器版本、明确的实验限制，以及五个允许交付文件的大小和 SHA-256。构建器最后调用同一核验器，核验失败不会报告成功。

从可信源码目录执行（摘要必须独立核对）：

```text
python scripts/verify_local_lab.py --bundle <绝对路径> --manifest-sha256 <可信的清单SHA256> --source-commit <期望提交>
```

核验器不会启动可执行文件、访问网络或改写包。它先验证外部给定的清单摘要，再检查严格字段、布尔类型、版本、文件列表、平台一致性、每个文件的大小和摘要。多余文件、缺失文件、重复 JSON 字段、路径穿越、文件替换、非普通文件、Windows reparse point 和超限输入均会失败。

不能从同一个未经验证的下载同时取得文件与摘要后，就声称来源已被认证。也不应先运行不可信包里附带的核验脚本。当前没有签名发布或可信更新系统。校验只反映检查时的文件，不能防止恶意本机在之后替换文件。

旧版 v1 清单明确拒绝，不自动重写为 v2；需要用新构建器重新构建，不迁移或删除钱包和节点数据。

## 依赖资料

`scripts/audit_crate_notices.py` 单独核验 Cargo.lock 记录的 crate 归档摘要并盘点归档内的许可证资料。其离线合成测试不等同于整个实际依赖集合已盘点完成，也不判断许可证兼容性。其输出保持 `distribution_approved:false`。源码构建与包核验同样不作法律许可判断。
