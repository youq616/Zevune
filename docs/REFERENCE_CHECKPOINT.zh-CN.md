# P2/P4：同步和提交前的参考账本检查点

状态：本机无价值资产开发功能。不是快照导入、账本扩容、网络匿名、主网或独立机构安全审计。

## 为什么接入实际使用路径

离线 `storage --expected-height --expected-app-hash` 已能完整重放后比较一个外部保存的准确检查点，但该命令返回时会释放账本锁。单独检查以后再执行 sync/submit 是两个独立的文件打开操作；不能把前者的结果当成后者一定使用了同一个状态。

新入口 `Network.SynchronizeAtCheckpoint` / `Network.SubmitAtCheckpoint` 按值接收检查点，取得原有真实 Rust worker 的独占账本锁并完整重放后，先读取 Status、比较起点的 **Height 与 AppHash 两者**，匹配才进入原同步逻辑。同一个 worker 和同一把文件锁保持到本次操作结束，不在检查与使用之间关闭/重开账本。原不带检查点的 API 保留。

错误检查点在第一次 RPC 调用之前拒绝，不访问节点、不追加区块、不广播、不释放钱包预留。校验和成功也不能跳过原有签名头、交易执行及下一份签名头 AppHash 的提交前检查。恶意本机或不遵守文件锁的进程仍不在保证范围内。

## 参数和结果

`sync` 和 `submit` 可选接受已有的配对参数：

```text
--expected-height <独立保存的准确本地高度> --expected-app-hash <独立保存的准确应用摘要>
```

其他 worker、网络配置、文件路径及端点参数保持原样。端点仍只接受数字本机地址。参数遵守已有规范十进制与非零小写十六进制规则，显式高度 0 是真实创世检查点；部分、重复或显式空参数拒绝。`sync --create` 不能和检查点一起使用，即使检查点高度为 0；本功能核对一个已存在的参考账本。缺失账本不自动创建。

检查点要从此前已可信验证并独立保存的状态取得。临时从当前候选文件读出高度/摘要再传回去，只能测试接口，并不能认证这份文件。它检查的是 **本次操作开始时的准确状态**，不是最小高度或祖先证明。比检查点更新的账本同样不匹配。同步可能合法推进到新高度，所以不能在同步结束时要求它仍等于旧起点。

同步和提交的 JSON 新增 `base_checkpoint_matched`。原不带参数的成功调用明确为 false。带参数的同步只有在全部成功时返回 true；同步失败仍不输出部分成功报告。提交在起点匹配后设置 true，但后续同步、交易检查或广播仍可失败，`confirmed` 保持 false。检查点失败的提交可以按旧的失败回执惯例输出 `status:not_submitted`、`base_checkpoint_matched:false` 和错误退出码，不能被解释成已广播或已到账。

同步后应独立保存返回的新高度和 AppHash，供下一次操作使用。若调用失败或回复丢失，同步可能已经保存较早的正确区块；不要自动回退到无检查点模式、删账本或解除交易预留，应先对账。此阶段不提供检查点文件的自动保存或可信签名。

## 验收范围

普通 Go 测试检查前置参数、显式创世高度、缺失上下文、新建模式冲突和未校验状态的 JSON。已有 storage 专用参数测试保留，只更新 sync/submit 现在有意支持配对参数的范围。

真实 operator 测试使用固定 Rust worker、真正 Orchard 证明及签名，覆盖完整旧前缀、同高度错误摘要、更新于准确检查点的日志、损坏日志、缺失文件和独占锁。HTTP 陷阱始终返回失败，仅统计不应提前发生的网络请求，不充当能接受假证明的共识节点。成功匹配后，陷阱内部再次尝试打开相同日志，以检查文件锁跨越验证与 RPC 阶段。匹配只允许进入原网络检查路径，不能使无效 RPC 成功。

原四节点真实 A→B→C、错误交易拒绝和重启测试逐字节保留；另建四节点真实场景，覆盖不带检查点的创建、带准确起点的 sync/submit、实际收款所在区块与独立重放一致。只在本机测试，不宣称多机、任意断电或全局最新性。
