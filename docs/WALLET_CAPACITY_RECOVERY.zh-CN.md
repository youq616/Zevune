# 钱包容量检查与满日志恢复边界

范围：P2 存储工作包的一项故障修复，继续使用原 `ZVWJNL01` 格式和 256 条保存记录上限。不是日志压缩、快照迁移、生产级长期存储或完整 P2 验收。

## 修复的问题

原 `WalletStore::sync` 在重扫之前无条件要求有空间追加记录。钱包日志达到上限后，即使只重建已经保存的同一个检查点，也会返回 `Capacity`。这会阻止重开钱包后识别余额和取回已加密保存的待发送交易，尽管这类同历史恢复并不需要新写入。

现在先核验拥有的文件，从已认证且由 `Zeroizing` 管理的快照建立临时候选钱包，重扫可信本地历史，然后比较需要持久化的状态。完全相同的检查点和待发送记录允许无追加恢复；只有状态确实变化时才要求空余记录。空间不足时在发布候选状态之前拒绝，原内存检查点和预留资产保持原样。实际写入/同步发生故障时仍停用存储实例，不能继续猜测是否成功。

恢复到原检查点不是最新状态或到账证明。若交易已确认、已过期或账本高度前进，需要保存新状态而日志又满，则仍拒绝并保留原待发送记录；不得因收到超时或容量错误就重签第二笔。后续生产存储工作仍需提供经过认证的整理/迁移及恢复方案。不能修改头部、删除历史、提高常量或伪造检查点来绕过限制。

## 实际操作入口

```text
python scripts/zevune_wallet.py --no-real-funds --backend <可信本地后端> --backend-sha256 <已核验摘要> --pin <独立保存的钱包回执> storage <钱包绝对路径>
```

回执选项仍是原接口，省略时无法检测整个合法旧备份的回滚。密码使用原来的隐藏输入并通过本地标准输入传递，不进入命令参数或环境变量。

新增 `storage` 操作使用有界 `ZVWCLI01` 帧、操作码 9、恰好一个钱包路径字段和原有可选回执。后端打开并锁定已有钱包、认证保存状态并检查当前文件，不扫描区块历史、不生成证明、不广播、不追加保存记录、不清除预留。旧后端会拒绝新操作码；没有自动回退。前后端须一起更新。

`result` 为 `storage_inspected_not_synced`。`wallet_storage` 包含：

| 字段 | 含义 |
|---|---|
| `format` | 固定为 `zevune-wallet-capacity-1` |
| `records_used` | 当前已保存记录数；不是付款笔数 |
| `records_remaining` | 在固定记录上限内尚能追加的数量 |
| `max_records` | 仍为 256 |
| `file_bytes` | 经检查的现有文件大小 |
| `max_file_bytes` | 当前格式的固定容量上限 |
| `can_append` | 仅表示记录额度未耗尽；不表示磁盘有空间或能够成功付款 |

Python 检查字段、整数/布尔类型、记录数、文件尺寸与上限的算术一致性。操作不返回余额或已确认状态，避免把文件检查冒充账本同步。检查可以更新操作系统的访问时间；不承诺读取完全不改变文件系统元数据。

## 验收与测试边界

新增完整容量测试通过真实加密和写入路径填满 256 条记录，包含一笔使用真实 Orchard 证明的待发送付款。重开后按同一历史重扫，取回完全相同的签名字节，回执和文件字节保持一致。之后真实提交付款并尝试同步新高度，在容量不足时拒绝，原内存检查点和预留未改变。备份包含原待发送字节且能够按原历史恢复。

重复的保存记录用于容量测试，不是宣称做了 256 笔网络支付；测试未使用接受任意证明的验证器。前端容量类型/边界、操作帧的所有截断、错误字段数量以及 Python 调用真实 Rust 后端的不改写检查分别覆盖。完整钱包和节点回归仍然必须通过，具体结果以准确提交的验收记录为准。

本修改不改变网络域、签名摘要、证明、电路、发行、费用、共识或钱包密码算法，也不访问用户原有数据。仅供无价值测试资产环境；未解决恶意主机、完整旧文件回滚、硬件故障或网络元数据匿名。

上游文件同步/锁语义参考： https://doc.rust-lang.org/std/fs/struct.File.html 。正常文件锁不替代恶意主机防护，文件同步也不是任意断电保证。

## 新的显式整理路径

`compact` 可把当前已认证快照和原待发送交易复制成新单记录日志，旧文件不变。它要求当前源回执，并产生新回执；不是自动恢复或无损取消支付。操作和跨副本边界见 [钱包日志整理](WALLET_COMPACTION.zh-CN.md)。节点账本容量与完整生产存储仍未解决。
