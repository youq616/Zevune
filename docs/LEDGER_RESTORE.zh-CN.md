# 多增量包公开账本恢复 v1

状态：候选模块，准确提交的原生验证与独立审核结果以模块 PR 为准；下述流程是实现合同，不是预先通过声明。

入口：`ledger_restore.py restore` 与 `verify`。本模块在现有 ZVARCP01 检查点、
ZVAIPK01 增量包和原 Rust 完整重放接口之上，完成一个基线加多个增量包的串联恢复。
它不是快照状态导入、自动追赶最新高度、节点激活或共识签名状态恢复。仍为 NO-FUNDS 本地实验。

## 1. 输入与信任

操作者独立保存并核对一个基线的**精确** ZVARCP01 检查点，以及每个增量终点的检查点。
每个检查点是 128 字节的 256 个小写十六进制字符。包内复制的检查点不建立信任，不能直接取来
作为外部可信参数。原恢复后端的 SHA256 也必须来自独立可信的构建记录。

一个流程接受一个基线、0 至 8 个增量包。每一步必须同一创世、相同头长度，高度和逻辑字节数
严格增加，段数不减少。原后端支持的同高度空包在这个编排入口中明确拒绝，不静默忽略、重排或
搜索丢失的包。只有基线、没有增量，也能恢复和核验。原旧格式、段大小及账本容量上限不改变。

提供错误的基线、回退/乱序终点或不匹配的包会失败；这些检查不能证明操作者提供的是全局最新
检查点。已经独立信任但过时的完整链，仍可能作为明确选择的历史恢复被接受。

开始前停止所有相关账本写入进程。底层每次操作使用原保留句柄、合作文件锁和完整重放；Python
编排不持有贯穿所有步骤的全局锁。对源和新输出的前后指纹比较不是授权、最终性或任意恶意主机
竞态下的原子快照。只允许规范目录、普通单链接文件，拒绝符号链接及 Windows reparse point。

## 2. 实际恢复

以下为 PowerShell 示例；`$P0`、`$P1`、`$P2` 和 `$BackendSha` 均来自此前独立记录。
从源码运行时给脚本加 `scripts\` 前缀；Linux 换为对应绝对路径和无 `.exe` 后端。

```powershell
python .\ledger_restore.py --no-real-funds restore D:\ZevuneRecovery\chain-001 --base D:\ZevuneArchives\base --base-checkpoint $P0 --step D:\ZevuneArchives\first.increment $P1 --step D:\ZevuneArchives\second.increment $P2 --reserve-bytes 67108864 --backend .\zevune-pool-recovery.exe --backend-sha256 $BackendSha
```

输入 `RESTORE-CHAIN` 明确确认后执行，不请求钱包密码。目标必须是**不存在的新目录**，父目录
必须已存在，不得在基线归档内部。不复用旧失败目录或空目录，不自动建立多层目录。

过程首先核对所有独立检查点和每个包头/物理长度，记录有界流式文件指纹，并真正验证基线。
通过空间预检后独占创建工作区：原后端 `restore-active` 建立 `stage-00` 基线完整副本；
随后每个 `restore-active-incremental` 都从上一完整阶段加一个包重建下一全新目录。每次仍经过
原真实授权、完整重放、物理帧边界、规范换段和最终检查点核验，不把预检结果复用为免验证权限。

完成全部恢复后，逐个原生 `verify-active` 重放所有新阶段，再用 `plan-active-incremental`
重新验证每对相邻阶段的字节前缀关系。两端各自合法而历史分叉，不能只靠高度递增被接受。
最终再次核对原基线和全部增量输入未改变，才创建 `RECOVERY.json` 并同步、回读及再查输出。

示例成功工作区严格包含：

```text
chain-001/
  stage-00/          基线的完整活动账本布局
  stage-01/          第一个终点的完整布局
  stage-02/          第二个终点的完整布局
  RECOVERY.json      由明确外部检查点序列决定的规范完成标记
```

阶段中只能有原 `genesis` 和连续 `00000000.journal` 等账本文件；不把清单放进活动账本目录。
所有阶段都保留，不删除中间数据来节约空间。成功 stdout 只有规范 JSON，确认提示和错误只写
stderr；返回 `completed:true`、末阶段固定相对名、高度、app_hash 和整个工作区保留的逻辑字节。
语法错误返回 64，认证/格式/容量/IO/超时错误返回 1，完整成功返回 0。

## 3. 独立复验

```powershell
python .\ledger_restore.py --no-real-funds verify D:\ZevuneRecovery\chain-001 --checkpoint $P0 --checkpoint $P1 --checkpoint $P2 --backend .\zevune-pool-recovery.exe --backend-sha256 $BackendSha
```

必须重新提供相同顺序的**全部独立检查点**。不信任标记自行提供参数，不从标记解析路径；程序
从外部参数重新生成唯一规范字节，逐字节比较标记，拒绝缺失、额外、非规范或错误的完成记录。
随后真实重放每个归档，并重新认证相邻前缀关系。复验不需要原基线目录或原增量包仍在原路径，
不会重建、修改或补登记任何文件。`input_sources_rechecked` 在 restore 为 true，在 verify 为 false，
避免声称再次检查了已不可见的原输入；复验仍检查完整恢复集。

即使恢复失败，没有完成标记的残留完整阶段也可以由操作者用原 `verify-active` 和该阶段独立
检查点另行核验。它不会被本模块自动标记为完成或续跑。一个已有完整标记也不是持久化未来保证。

## 4. 空间、时限和错误

预算保留每个阶段的**全部**数据，不仅计算增量大小。最多 9 个各受原 1 GiB 上限约束的归档，
加目录/文件分配取整及标记和显式保留量。Linux 按每文件至多多分配一个单位减一字节保守计算，
并检查所需 inode 数；Windows 沿用调用者可用量，未知分配单位或 inode 不伪造为已检查。
这不是空间预留，也不包括可精确预测的 COW/元数据/ACL/其他进程开销。

每个固定后端命令最多 300 秒，整个 restore/verify 调用使用一个 1800 秒绝对期限。
期限从入口开始，包含初始文件指纹、标记读取、空间查询、每次原生调用、末尾再核验与完成标记写入。
流式读取逐块检查同一期限；后端二进制摘要核对、进程创建和读取线程启动也消耗原命令预算。
任何检查耗尽预算后，不能重新获得时间、启动下一恢复命令或报告完整成功。
已经进入内核的 I/O 在返回时再次检查：过期可能保留部分或完整结果，但不返回成功。
不降低或提高原底层程序测试预算。
OS 打开/读取/创建操作本身不一定能被 Python 时钟中断，因此不能称其为所有内核调用的硬时限。
stdout 最多 198656 字节，stderr 最多 4096 字节，以独立线程同时有界读取，避免无界
communicate 缓冲或互相阻塞；错误、超时、超限均失败并回收直接子进程。可信后端无子进程，
不声称可以杀死任意恶意程序私建的进程树。
正常返回、超时、读取线程创建或启动失败都须回收已创建的子进程并收尾已启动的读取线程。
终止确认共享一次5秒窗口，两个读取线程共享一次2秒清理窗口；finally不能重新开始任一窗口。
读取线程在其自身finally关闭所拥有管道，未启动或已经退出的线程对应管道由主线程关闭，避免主线程
在活跃BufferedReader锁上无界等待。无法确认回收或线程退出时仍报错，不标记完整成功。
这些拒绝路径的回归使用真实失败/阻塞子进程、受控时钟和线程故障，不模拟成功认证或账本重放。

错误可能留下已认证的早期阶段、不完整或完整的晚期阶段、部分或完整标记。**全部保留，不删除、
覆盖、截断、盲重试或自动回滚。** 包内容错误可能在新工作区已存在后才经真实重放发现；这些输出
不是部分入账，因为它们从不接入现有活动账本。stdout 丢失也不能推断磁盘上没有完整输出。

## 5. 恢复后不等于节点恢复

成功始终 `snapshot_imported:false`、`finality_verified:false`、`validator_ready:false` 和
`real_funds_allowed:false`。不要把工作区末阶段直接当成已完成共识/验证者恢复。
它不包含共识数据库、WAL、验证者密钥、最后签名状态或钱包，不重置签名器，不执行网络上线。

需要继续本地账本实验时，明确用原 `restore-active` 和末端检查点复制到另一个新活动目录；
保留这套恢复集不可变。原集成测试会从这个独立副本完整重开，拒绝重复付款，构建真实后续付款，
再重开核对余额和费用。该证据不构成生产节点重启、安全经济规则或多机可信同步批准。
