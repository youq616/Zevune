# P7：单次请求、增量提案筛选

状态：开发中的无价值资产实验网络优化；不改变交易有效性、发行、共识投票门槛或账本格式。不是完整性能验收、网络匿名或主网准入。

## 实际调用路径

`poolapp.PrepareProposal` → `poolbridge.SelectProposal` → 本地 Rust worker 操作5 →
`PoolStore::select_proposal` → 与完整区块执行共享的 `State::apply_transaction`。

原实现依次预执行 `[tx1]`、`[tx1,tx2]`、`[tx1,tx2,tx3]` 等全部已接受前缀。
新实现对已提交状态建立一个临时候选，按输入顺序逐笔尝试；单笔检查全部成功后才更新
该临时候选。无效候选不会污染后面的交易。费用加法、容量、密码学及新树前沿的计算
全部在更新资产集合之前完成。可信历史根始终取区块前的已提交状态，同块新输出不能
成为后续交易的已提交花费根。

候选状态在返回时丢弃。现有授权验证缓存仍只缓存准确字节的密码学成功，不缓存当前
账本允许花费的结论。`ProcessProposal`、`FinalizeBlock`、`Commit` 及日志重放仍独立执行
完整区块检查，不复用筛选作为提交许可。筛选也不覆盖 Rust/Go 的待最终提交槽。

## 范围和原策略兼容

最多检查原始请求的前64项，保持原顺序，最多选16笔，总交易字节不得超过
`RequestPrepareProposal.MaxTxBytes`。无效长度跳过，但不因此继续查看第65项。
无效证明、域不匹配、到期、双花、重复输出及费用溢出仍拒绝相应候选；操作或存储故障
不得转换为接受交易。空预算仍验证请求高度，而不是跳过高度检查。

16笔全部有效且可装入时，原算法的候选交易应用次数为1+2+...+16=136，新算法为16；
原IPC调用包括一次空预检查与16次前缀预检查，新算法合为一次请求。
这是算法工作次数，不是实测时间加速倍数。原缓存本已减少重复证明验证，所以不能说
把136次真实证明验证减少到16次。当前测试计数器只存在于测试构建，不收集生产交易信息。

## IPC 第3代（仅本地公开数据管道）

新握手指纹输入为：

```
ZEVUNE-POOL-IPC-3:zevune-orchard-lab-1:16:28134:selection-64
```

旧客户端和新worker必须握手失败；升级时成套更新，不自动退回旧请求协议。
交易仍为原LAB1/LAB2，日志仍为原ZVOPOL01/ZVOPOL02；没有链状态迁移或改写。

操作0至4的消息语义及145字节回复保持不变。新增操作5的载荷为：

```
u64be(height) || marker[32] || u64be(byte_budget) || u16be(count) ||
    repeated(u32be(length) || exact_transaction_bytes)
```

预算最多450144字节，候选最多64，每项长度最多28134。空项可解码但不被选中。
回复仍绑定请求编号与完整请求SHA-256；在原145字节回复后追加8字节大端位图。
第i位对应第i个候选，最高第63位。正常拒绝的位图必须为0。Go再检查位数、范围、
选中数量、长度、预算和返回高度；不可能的回复关闭worker，而不当作普通交易拒绝。

输入帧容量仅为支持一次有界候选集合扩至2MiB，实际最大载荷由64项上限进一步约束。
普通区块仍最多16笔；这不提高网络区块字节上限。副作用仅有现有过程内密码学成功缓存，
不写钱包、不写日志、不触碰验证者密钥。调用取消或超时仍关闭该验证进程，没有自动重试。

## 验收要求

使用真实Orchard付款对比旧前缀算法和新筛选的选择结果与状态摘要，覆盖顺序变化、
字节预算、无效签名、错误网络、重复候选、同块未提交根、过期及重启后的已花费检查。
检查临时预执行不会改变已提交状态或日志；检查费用溢出在最后阶段拒绝也不会留下
部分更新。真实Go/Rust/ABCI联调检查第64项、忽略第65项、已Finalize时进行筛选不覆盖
待提交交易。合成进程只用于Go协议边界测试，不替代真实证明或运行验证器。

性能仍需后续记录证明生成、广播、共识、落盘和收款确认的完整分布；本功能不提供
端到端p95、TPS或5秒到账的实测结论。大量恶意候选仍有验证成本，2MiB有界请求不是
完整抗滥用方案。P1协议升级、P2节点长期存储、P3多机和P5网络隐私均不因本优化完成。
