# Zevune 整体验收标准

用户已确认 M1/M2 在 Windows 上可用，要求不再对每个小改动进行手工验证。后续开发以开发者回归测试、GitHub 自动测试和整合交付为主；不要求用户反复安装、查询状态或贴日志。仅用户侧特定环境无法复现的问题或重要产品决策才需要用户参与。

## 当前模块边界

M2 单机程序继续使用 0.1.2-dev 及原日志，不自动迁移或清空数据。M3 共识实验位于独立的 integration/cometbft 模块，使用单独的数据目录和 zevune-consensus-lab-1 链标识；其 0.2.0-consensus-dev 版本不代表钱包或隐私支付已完成。

Go 根模块与嵌套共识模块必须分别测试。不得把根目录 go test ./... 的成功当作已经运行嵌套模块测试。任何 main 发布都必须核对明确提交对应的测试记录。

## 集成支付版本交付门槛（目前尚未达到）

1. 已选定并审查完整的成熟隐私支付协议，包括发行、权限、金额范围、守恒、双花防护与接收解密；不是把哈希或测试校验和当成零知识证明。
2. 钱包能够在用户本地创建和恢复测试账户，完成真实证明生成及无价值测试资产收付款；服务端不索取花费密钥、查看密钥或支付明文。
3. 多节点对含真实有效证明的区块取得一致状态，拒绝伪造证明、越权花费、增发和重复花费；签名提交与应用状态必须相互绑定。
4. 节点与钱包的正常重启、网络中断、部分节点离线、存储错误等场景经过自动化回归；不通过删除签名状态或关闭验证来恢复服务。
5. 在明确的设备、网络、负载和统计窗口下记录端到端支付延迟，分别报告证明、传播、提交、收款识别阶段。空块时间、哈希基准和测试耗时不是到账速度。
6. 明确列出公开元数据、日志内容、用户设备及交易对手信息泄露的保护边界。不承诺绝对匿名，也不设置全网查看密钥。
7. Windows 和 Linux 自动构建、模块锁定、依赖审查与整合测试形成可复核记录；整包操作说明不依赖开发者口头补丁。

在以上门槛达到之前，不把当前成果称为完整隐私链。外部安全审查、验证者独立运营、经济规则、主网启动和真实资金准入仍需要单独决策；测试通过不等于独立审计。

## M3 专项验收

四个独立进程进行真实 CometBFT 通信和签名；在共同高度核对区块哈希、应用哈希以及签名门槛；观测 3/4 在线继续出块与 2/4 在线停止；恢复在线节点、滞后节点追赶、强制结束进程及全体重启。只处理空区块，所有交易入口拒绝。

所有进程同机运行，只能用于本地集成验收，不能称为四个独立运营主体或跨地域网络。M1 的有限日志容量仍然存在，不适合长期无人值守运行。
