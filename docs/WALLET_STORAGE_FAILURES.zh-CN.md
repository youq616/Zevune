# P2 加密钱包的实际空间耗尽与恢复

本阶段接续 [PR #20](https://github.com/youq616/Zevune/pull/20)，基线为 `313ec90462cbaa8824b356435d08678f2a1d09ec`。上一阶段已覆盖活动账本的 Linux tmpfs 空间耗尽及双平台 worker 进程故障；本阶段补充加密钱包文件本身的真实写入失败。准确候选、非作者独立审核、完整原生 CI 和最终合入身份记录在本阶段 PR。本文描述测试合同，不能单凭测试定义认定已经通过。

## 1. 范围与恢复原则

已有 [`WalletStore`](../integration/orchard/src/wallet/vault/store.rs) 将付款预留与精确签名 outbox 保存到同一加密记录。保存失败后，当前实例关闭对余额、回执、pending 和后续写入的访问；整理副本则在新文件完整写入、同步及认证验证成功后才退休源实例。原私有 `cfg(test)` 部分写入与确认丢失测试继续保留。本次通过公开 API 和实际 Linux ENOSPC 检查这两个不同的失败边界。

| 场景 | 真实失败点 | 必须保持的恢复条件 |
|---|---|---|
| 已确认付款的状态保存失败 | 原付款与预留已正常保存；账本实际提交后，`WalletStore.sync` 追加新检查点并清除 outbox 时写满 | 当前实例不可用；原完整加密前缀不变；损坏后缀保留且普通重开拒绝。从事前好备份恢复，先核对旧历史下的原 outbox 和预留，再以真实新历史确定已确认状态 |
| 整理副本写满 | `compact_copy_new` 创建新目标并写入首条加密记录时空间耗尽 | 源全部字节、精确回执、outbox 和预留保持，源实例仍可使用；部分目标保留、拒绝打开和覆盖。只有另选新目标完成写入及验证后，才能退休源实例并交接新回执 |

付款均为临时无价值测试资产，使用现有真实 Orchard 证明和授权。没有新增密码算法、钱包格式、生产故障参数、自动重试或自动删尾。钱包原 256 条记录上限及活动账本原容量规则保持。

`WalletStore` 对文件错误返回 `StoreError::Io`，该枚举没有原始 errno。仅看到这个错误，或仅看到填充文件的 ENOSPC，都不能证明目标钱包写入确实遇到空间耗尽。外部系统调用证据与 Rust 状态、文件和恢复断言必须同时成立。

## 2. 固定实验环境

[`wallet_enospc.rs`](../integration/orchard/tests/wallet_enospc.rs) 定义两个 Linux + `local-funding-lab` 的 ignored 集成测试。普通测试不会自行挂载文件系统；[`active-storage-faults.yml`](../.github/workflows/active-storage-faults.yml) 分别编译并执行固定的 `active` 和 `wallet` suite，每个 suite 有独立 CI 任务和证据。原活动账本两例继续完整执行，不能由钱包测试代替。

[`run_active_enospc.py`](../scripts/run_active_enospc.py) 的 `--suite wallet` 仅接受两个固定测试名和对应目标路径。普通 runner 编译锁定依赖；监督器在私有 mount / PID namespace 中为每例创建新的 **8 MiB tmpfs、256 inode** 文件系统。测试与 strace 降权到普通 runner 身份；填充循环有固定字节上限，不使用宿主文件系统制造空间耗尽。

每例 180 秒、namespace 420 秒、root watchdog 430 秒及其后 5 秒 KILL 期限保持。独立 probe 实际检验忽略 TERM 的 root namespace 能被回收。普通卸载、namespace 退出和控制目录清理均须得到确认；环境缺失、漏跑、超时、输出超限或清理未知均不接受。两个 suite 的 matrix 不因另一例失败而取消，以保留各自的真实结果。

每例 strace 仅过滤一个精确目标路径，观察 write 系列及同步调用，写参数采用 raw 且只记录失败结果。原始 trace、任意 stderr、交易及密钥材料不会打印或上传。公开证据只保留固定 schema 的源提交身份、suite、目标身份、密文文件摘要、独立回执摘要、错误计数、断言及清理状态。监督器另外读取目标文件和控制目录内固定证据，核对实际 inode、长度、摘要和独立 pin，不只信任测试输出的布尔字段。

## 3. 追加失败与事前备份

钱包固定文件头为 72 字节，加密记录为 32948 字节。创建、按真实创世同步并准备首笔付款后，三条记录共 98916 字节，尾页还剩 3484 字节。填满 tmpfs 的其他可分配页后，确认付款的同步追加会先利用这部分已有空间，再在分配新页时失败。因此必须观测到真实部分追加，不能只验证一次写入返回错误。

测试保存事前独立 `StoreReceipt` 和卷外好备份。故障后核对原完整加密前缀、实际部分后缀及文件长度，检查所有相关公开操作拒绝；关闭后普通打开和携带原 pin 的打开均不得修复文件或返回可用钱包。

恢复使用原好备份及事前 pin，显式复制到新路径。打开后必须先处于 `NotSynced`，按旧的已验证历史恢复完全相同的 pending ID、签名付款字节、余额和预留。随后从实际账本冷重放取得已确认的新历史，才能清除这笔 pending 和预留。恢复不能通过重新构造或重新签名另一笔付款消除不确定状态。

成功同步到较新历史后，再次提交旧历史必须返回回滚错误，且钱包全字节、回执、余额和 pending 保持，不能重新建立已清除的预留。测试还需实际提交下一笔真实付款，核对余额、手续费与完整账本状态，拒绝再次花费两笔已花付款，再关闭并重开钱包和账本检查状态。好备份及故障源的原始字节在整个核验期间保持。

## 4. 整理目标失败与回执交接

源钱包位于卷外，已经正常保存真实 pending 及独立回执。测试在专用 tmpfs 中创建目标目录，填满后仅释放填充文件的一页，以便新目标写入文件头及部分首条记录，然后真实失败。目标保留实际写入结果；再次选择同一路径必须拒绝覆盖。

失败不应使健康源退休。测试核对源全字节、精确回执、原 pending 字节和预留，并通过正常操作确认源仍有效。随后显式选择卷外另一个新目标完成整理，核对新旧回执交接、源实例退休、新副本 `NotSynced`、相同 outbox 和重新同步后的预留。

新 journal 有新的随机身份，旧回执不能认证这个新 journal。新副本只能使用整理返回的新回执；旧源及其副本不能被密码学远程撤销，文件锁也不协调多份钱包同时花费。本实验不会将源实例退休解释为所有历史备份都已失效。

钱包加密记录使用随机材料，不能把另一轮成功生成的密文当成故障后缀的逐字节参考。测试核对原加密前缀与公开帧边界，再通过现有认证解密和真实账本历史核对恢复后的同一笔付款。

## 5. 验收与未覆盖边界

冻结 base / head / tree 后，未参与实现的独立任务分别审核钱包不变量、监督器与证据边界、工作流和文档。修复阻断需要复核新候选。原 Go test / vet / race / decoder fuzz、Rust 普通和 funded 测试、双平台付款与增长场景均继续核对准确候选的实际日志，条件跳过单独记录。

本阶段只检验 Linux tmpfs 的真实空间耗尽。它不覆盖 Windows ENOSPC、物理介质损坏、文件同步 I/O 错误或断电，也不证明 Windows 目录同步语义。`backup_new` 的复制写满、付款首次保存写满、CLI 导出写满及钱包进程强杀仍需专门场景；现有模拟故障测试不能改记为这些真实 OS 试验。

P2 的持续真实付款与完整容量、快照状态导入及防回滚、物理存储与同步/断电试验继续开发。完整在线钱包、多机网络和长期运行按[交付计划](DELIVERY_PLAN.zh-CN.md)继续推进。`snapshot_state_import_implemented`、`production_storage_ready`、`audited` 和 `real_funds_allowed` 保持 false。
