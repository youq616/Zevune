# 钱包安全整理执行与交接核验 v1

本模块接续只读 `wallet_health.py`，提供真正执行的 `wallet_maintenance.py compact` 与独立
`verify`。它属于 NO-FUNDS 本地钱包运维，不是在线钱包切换、交易授权或生产资金批准。
模块范围是一次明确的“完整备份 → 原生整理 → 重新认证 → 保存交接清单”，不是维护任务调度器。

## 1. 前提和信任

需要 Python 3.10+、Linux 或 Windows，以及独立核对 SHA256 的原 `zevune-wallet-local` 后端。
必须提供此前独立保存的**精确源钱包末端回执**。工具不从源文件自行生成受信回执，不接受旧祖先
回执代替末端，也不以公开散列代替密码认证。密码只通过不回显终端和子进程 stdin 传递，不能放进
命令行或环境变量。源及全部目录须已存在、规范、不通过符号链接或 reparse point。

执行前停止其他钱包进程，确认没有人会同时修改或操作源钱包。程序沿用原后端逐次打开时的文件锁，
但**不持有跨整个编排过程的全局钱包锁**。它在关键步骤和结束时重查源字节和身份；外部变化可能
导致失败并留下输出。成功后源仍可被另一个进程打开，旧密钥也没有被撤销。不要并行从副本付款。

## 2. 创建一次交接

以下为 Windows PowerShell 示例。`$Pin` 和 `$BackendSha` 来自独立保存的可信记录；不使用密码变量。
从源码运行时在脚本前加 `scripts\`，Linux 使用对应路径及无 `.exe` 后端。

```powershell
python .\wallet_maintenance.py --no-real-funds compact D:\ZevuneRecovery\handover-001 --source C:\ZevuneData\wallet.journal --pin $Pin --backend .\zevune-wallet-local.exe --backend-sha256 $BackendSha --reserve-bytes 67108864
```

目标必须是**不存在的新目录**，其父目录须存在。不自动建多层目录，不复用空目录或上次失败的目录。
输入 `MAINTAIN` 明确确认后，才询问隐藏密码。`--reserve-bytes` 必须明确给出，可为 0；示例 64 MiB
只是用户策略，不是协议最低值。无效参数错误退出 64，认证、空间、写入或验证错误退出 1。

执行流程：

1. 用原 Rust op9 认证精确源文件，检查目标父目录身份与空间预算。
2. 以独占目录创建取得本次输出名，在新目录内用原 op2 创建 `backup.journal`；比较完整密文字节并重新认证。
3. 对这份**刚刚认证的备份**运行原 op10，创建 `compacted.journal`。不是对活动源执行原地整理。
4. 原 Rust 实现比较完整解密快照与精确待发送 outbox；Python 再用原 op9 认证一记录新钱包，重查备份与源。
5. 最后以只创建方式保存规范 `HANDOVER.json`，同步文件和支持的平台目录，再从磁盘完整核验三文件。

输出目录严格只有三文件：完整旧密文、单记录新密文、交接清单。旧文件不删除，整理不计作回收
旧空间。原 256 记录上限不变，新文件从 generation 1 开始**新祖先链**；原回执不能认证新文件。
程序成功返回新的 `target_receipt` 与 `handover_sha256`。将二者及原源回执独立保存，不只保留在
交接目录内部。回执和摘要不是密码，但可关联钱包版本，不能把它们上传公开日志或仓库。

## 3. 独立核验与之后的操作

```powershell
python .\wallet_maintenance.py --no-real-funds verify D:\ZevuneRecovery\handover-001 --pin $Pin --handover-sha256 $HandoverSha --backend .\zevune-wallet-local.exe --backend-sha256 $BackendSha
```

`verify` 不要求活动源仍在原路径，但必须用独立保存的原回执和交接摘要。它拒绝额外或缺失文件、
非规范/重复键清单、错误类型、错误长度、旧回执、文件/目录身份变化及密码认证失败。它认证目录内
两份精确文件，不签名、不扫描历史、不修改文件、不补清单。公开链或清单摘要不能替代原 Rust AEAD。

交接清单是**操作者固定的回执对**，不是可移植的密码学祖先证明。创建时的真实 op10 检查完整状态
和 outbox 相同；之后 `verify` 依靠独立保存的清单摘要和两份真实认证，不能凭任意自制清单证明两个
钱包属于同一用户。清单只保存固定字段，无输入决定的路径、外部程序、脚本或任意解包内容。

成功仍为 `requires_rescan:true`、`active_wallet_replaced:false`、`source_not_revoked:true`。
下一步由操作者明确选择一个活动副本，使用原钱包工具与新回执扫描可信历史、核对原待发送付款，
再决定是否使用它。**本模块不自动激活、不更新配置、不撤销旧副本、不释放预留、不重新签名或广播。**
为了让原交接可继续核验，不应直接将目录内的 `compacted.journal` 长期作为活动文件写入；应先用
原复制/恢复流程创建新活动文件，再保留此目录离线。任一文件更新后，原精确交接核验会拒绝。

## 4. 空间与失败语义

预算同时包含完整备份 W、一记录新钱包 33020 字节、最多 4096 字节交接清单及显式保留量。
Linux 对三个文件分别按采样分配单元向上取整，并要求可用 inode 至少 4（新目录及三文件）；
Windows 分配单元/inode 未知时明确使用逻辑数据预算。查询沿用上阶段的调用者可用空间与独立路径
采样，不把卷级空闲、root 保留块或旧钱包“整理后可释放量”算入可用空间。

这是保守数据预算，不是磁盘预留或未来写入保证。文件系统元数据、COW、压缩、配额、ACL、其他进程
和设备错误都可能改变结果。源日志已经满不会阻止对新文件整理；它不需要在源上追加任何记录。

错误可能留下空目录、完整备份、不完整新钱包，甚至两份完整文件与部分/完整清单。**一律保留，
不自动删除、覆盖、截断、补登记或重新执行。** 未拿到成功回执不能推断没有写入。无完整且独立固定的
交接清单时，不得把残留新文件当自动激活依据；原源和已认证备份仍是人工核查的基础。

## 5. 测试和交付范围

v7 程序包增加本工具和本指南，为 16 个 payload 加 manifest；v2-v6 原精确合同保留。普通命令行
运行不要求 `-B`；入口在本地模块导入前禁写字节码，库导入不修改宿主策略。

定向测试覆盖三文件预算、四目录项、边界、独立摘要、精确回执、规范清单及错误参数不泄密。原生
生命周期在两平台重新构建原 Rust 后端，实际创建无付款/有pending钱包，验证完整备份、一记录整理、
独立复验、相同pending签名字节/交易编号及 available=0 预留；并核查丢失备份/整理回执、部分清单
写入时的残留和重复操作拒绝。故障驱动仍真实执行后端，不存在接受任意认证的替代实现。

重新计算全部公开散列后的真实密文篡改必须到达并被原 AEAD 拒绝。回执丢失与清单写入故障是受控
错误测试，不是新真实 ENOSPC、进程强杀或物理断电证据。没有改变生产 Rust/Go、密码学、钱包格式、
同步/锁、依赖锁、记录限额或旧测试预算；准确候选审核和原生结果以本模块 PR 为准。

仍假设可信本机、规范父目录及批准后端，不保证恶意主机竞态、Python密码内存安全擦除、Windows
完整 ACL/目录断电持久性。Issue #23 和 P2 整体保持未完成，`real_funds_allowed=false`。
原生创建/同步语义参考 Python 官方 `Path.mkdir` 与 `os.fsync` 文档，不构成项目安全背书：
https://docs.python.org/3/library/pathlib.html#pathlib.Path.mkdir
https://docs.python.org/3/library/os.html#os.fsync
