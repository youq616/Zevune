# 每阶段独立子代理审核

自2026-09-14起，每个阶段在代码开发和回归测试之后，必须由未编写该候选的独立编码代理任务/会话审核。此规则补充八工作包计划，不新增一个产品功能模块。

## 提交与审核流程

开发者将候选推送到现有统一开发分支并建立PR，不直接快进主分支。PR记录准确的基线提交、候选提交、源码树、改动范围、实际测试和未测边界。独立审核者应读取代码与调用方，而不只是阅读作者的验收摘要。

本会话没有直接启动子代理的工具时，可通过仓库已启用的GitHub编码代理审核渠道发起单独任务；必须确认实际收到审核结论。发出请求、出现表情回应、CI通过、作者换一个角色自查，均不代表独立审核完成。仓库未启用代理时，记录“审核渠道待启用/审核待执行”，候选留在开发分支，不以自查替代。

审核记录至少包含：审核者或任务身份、覆盖的base/head/tree、检查范围、发现及严重性、建议和复现、未能执行的测试、结论及原始结果链接。若服务只检查高严重性问题，应如实记录该范围，不能说它完成了所有级别问题的全面审核。

发现阻断问题后，开发者修复并重跑回归；修改运行代码或测试后，对新提交重新请求审核。仅补充审查记录的后续文档提交必须核对运行源码逐字节未变，并保留被审核的原始提交身份。

## 合入条件

必须同时具备：真实调用路径、相关CI通过、必要的真实密码学/状态恢复证据、独立代理针对当前候选的结果、阻断问题关闭、未测边界明确。未收到结果或结果针对旧提交时，保持“待审核”。不得修改项目状态文件把尚未验收的P1至P8模块标为完成。

这是一条明确的开发流程要求，不是已经配置好的GitHub服务器端强制分支保护。代码与仓库权限不能从内部证明管理者无法绕过规则。本规则也不等于独立机构进行的协议、密码学或安全审计。
