# 原生后端校验安装器 v1

本模块把独立批准的原生程序字节复制到一个全新的、只有一个硬链接的本地文件。它解决构建产物和
执行路径之间的交付问题，不放宽历史交易查询对原生程序的单链接要求。安装器不运行程序，也不访问
钱包、账本或网络；所有命令均要求 `--no-real-funds`。它不是公网部署授权或正式软件发布。

## 两个命令

从可信工具目录运行；需要 Python 3.10+，不需要 Git、Rust、Tk 或钱包密码。Windows PowerShell：

```powershell
python .\scripts\native_backend_install.py --no-real-funds install --source 'C:\ZevuneBuild\zevune-pool-recovery.exe' --destination 'C:\ZevuneApproved\zevune-pool-recovery.exe' --backend-sha256 '<独立确认的64位小写SHA256>'
python .\scripts\native_backend_install.py --no-real-funds verify --backend 'C:\ZevuneApproved\zevune-pool-recovery.exe' --backend-sha256 '<同一独立SHA256>'
```

目标父目录必须预先存在；目标文件必须不存在。已有文件、目录、空文件或悬空链接均拒绝，不覆盖或
自动升级。两个路径均须绝对、不含 `..`，文本及UTF-8字节长度有界。拒绝符号链接/reparse父目录与
非普通源文件。Linux使用对应绝对路径；目标文件名由操作者明确选择。

摘要必须来自独立可信渠道，不能从收到的可疑文件自算摘要并赋予信任。安装后的路径和同一摘要应交给
历史交易查询的 `--backend` / `--backend-sha256`。安装器不会自动更新配置、PATH、注册表或服务。

## 源允许硬链接，执行目标不允许

已停止变动的构建产物可能有多个硬链接。只有 `install --source` 允许它作为复制输入；原摘要检查、
普通文件及身份检查仍全部执行。源文件和任何别名都不被删除、改名、改权限或拆链接。

目标使用仅创建的文件打开方式，逐字节复制而不是创建硬链接；核验目标与原批准摘要一致且只有一个
硬链接。原生查询仍拒绝直接执行多硬链接文件，安装成功也不会让原源路径自动获得执行许可。

`verify` 只检查单链接文件和摘要，不复制、不修复链接、不启动程序。即使摘要一致，有第二个链接也
拒绝。外部写入者、编译器或恶意进程仍可能修改文件，使用前必须停止写入并信任本机与父目录。

## 完整性不等于程序已经验证

成功需退出码0，并且JSON标志符合预期。输出固定包含 `integrity_verified=true`、
`single_link_verified=true`。仅安装命令额外有 `installed=true`、`source_unchanged=true`。
以下标志始终为false：`executable_started`、`protocol_verified`、`code_signature_verified`、
`platform_compatibility_verified`、`accepted`、`real_funds_allowed`。

工具不识别文件是不是原恢复器、是否适合当前平台、是否有有效数字签名或是否已经通过安全审核。
它也能复制独立固定摘要的其他字节；这个事实不能被称作通过原生协议验证。真正的协议/账本核验仍由
后续明确执行的原生工具完成。安装本身不发起这一步。

## 写入与失败语义

先用原 `Backend._check` 完整核验源，再打开全新目标。源最大512 MiB，复制缓冲最多1 MiB，累计长度
和复制摘要精确匹配；短写继续处理，零写或写入/同步/关闭错误失败。源的路径与句柄元数据各自保持
自己的基线，不把Windows两类查询的时间戳强行等同。

每次调用共享300秒预算，不自动重试或续期。文件系统阻塞、原摘要检查或关闭可能超出墙钟时间；
过期不能报成功，但不是硬实时取消保证。目标请求POSIX模式0700，受umask约束；Windows采用父目录
与系统权限，不能据此声称完整ACL加固。

复制后完整重读源和目标，检查源未改变、目标仍为创建的对象且单链接。Windows关闭写句柄可能最终
更新文件时间戳，因此跨关闭检查对象身份，随后完整重算摘要并固定最终路径元数据，而不是跳过校验。
没有目录fsync、跨文件全程锁或原子激活保证，也没有物理断电、恶意内核/文件系统或校验后持续监控保证。

任何失败都保留原文件及部分/完整新文件，不自动删除、回滚、覆盖或续装。失败可能留下摘要正确的完整
副本；另一次 `verify` 成功不代表前一次安装调用成功退出。不要运行失败留下的半成品。返回码为：
成功0，失败1，参数错误64，中断130。错误使用固定提示，不回显路径或底层异常；输出和退出码必须一起核对。

## C19失败的修复和测试

C19两平台原生测试在首份真实恢复结果之后触发 `single_link_lookup_backend_required`：直接把构建目录
产物当作执行路径，未满足刚新增的单链接安全门槛。本轮保留该拒绝，在真实测试驱动内通过本安装器CLI
创建独立副本，核对同一摘要/单链接/不同文件身份后，再运行原有完整恢复和历史查询场景。

原有真实硬链接后端拒绝测试保留。临时副本仅由测试驱动创建和清理；产品安装器本身不删除任何文件。
没有重新实现验证器、接受型密码学替身、预算放宽或删减场景。单元测试使用惰性字节，只证明复制与拒绝
规则；双平台原生集成才测试原程序能否在安装后正确运行。

参考：Python官方 `os.open`、`os.fstat`、`os.fsync` 文档与原 `wallet_backup_backend.py`。
此阶段仍需准确提交的独立非作者审核及CI；不自动合入main，P2/P4整体、历史问题及NO-FUNDS边界保持。
