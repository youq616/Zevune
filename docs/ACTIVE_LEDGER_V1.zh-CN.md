# P2 活动账本分段第一版设计

设计日期：2026-09-17。基线 `2b889d52c2e6c765f03ea683f42b8467d66e47f5`。
状态：冻结候选，须由独立设计审核通过后实现；此文不是实现或测试通过证明。

## 目标与兼容

本阶段在统一 LAB2 真实 Orchard 执行路径中增加活动日志分段，交付正常
PoolStore → worker → Go 的连续提交、轮换、完整重放、重开后继续提交及钱包历史读取。
新建的无价值资产实验网络可明确选择此版本；不迁移、覆盖或升级既有网络及用户数据。
旧 LAB1/LAB2 的单文件格式、10000 条/64 MiB 限制、签名语义和恢复工具保持原契约。

新公开测试创世清单使用 `ZVTGEN03`，布局与 `ZVTGEN02` 相同（82 字节头和每项115字节
公开分配），magic 唯一标识固定 `ActiveSegmentsV1` 容量规则；不是任意参数配置。
仍验证固定100000公开测试单位、全部真实曲线点、承诺唯一性和非零部署 nonce。
`TestGenesis::generate_active` 明确生成新清单；已有 `generate` 仍生成02。
03 的完整清单 SHA-256 仍作为 LAB2 付款签名域，因此与相同公开分配及 nonce 的02隔离。
交易编码、Orchard证明/授权、资金守恒与状态摘要算法不变。

活动初始账本头使用 `ZVOPOL03`，其余布局同有域绑定的 `ZVOPOL02`；头内绑定清单摘要和
初始承诺。该头的摘要进入原 `State.genesis`，容量profile因此绑定应用摘要及PreparedBlock.base。
只接受可信03清单配03头；01/02清单禁止打开活动目录，03清单禁止退回旧单文件。
旧 header/recovery 解析器继续拒绝03；共享重放只有在显式活动profile下接受新头。

| 固定规则 | 旧单文件 | ActiveSegmentsV1 |
|---|---:|---:|
| 最高区块高度/总记录数 | 10000 | 1000000 |
| 累计逻辑字节（头+完整记录帧） | 64 MiB | 1 GiB |
| 单活动段最大字节 | 无 | 1 MiB |
| 最大段数 | 无 | 2048 |
| 每块交易数/承诺总数 | 16 / 65536 | 16 / 65536（不变） |

段数独立设置为2048，以容纳记录不得跨段产生的尾部剩余空间；总逻辑字节和段数都检查。
这些仍是有界实验规则，不能称无限增长或生产存储。防双花、承诺集合、状态复制及摘要扫描
仍在内存，完整钱包历史也有随历史增长的成本；本阶段不宣称已解决这些独立容量问题。

## 文件、锁与轮换

活动账本路径是仅新建的目录：不可变 `genesis` 头文件，以及从
`00000000.journal` 开始的八位十进制连续段名。段仅存原 `ZVOBLK01` 完整帧，无额外段头。
每帧仍为 `u32 body长度 + 原body + SHA-256(body)`；空块150字节，每笔另加4字节及原交易。
高度、base/result应用摘要和真实授权把段内外记录连接成同一历史；校验和不是授权。

`genesis` 文件的独占锁覆盖整个活动目录的生命周期。保留根目录句柄和当前活动段句柄；
拒绝 symlink、Windows reparse point、Unix多硬链接、非普通文件、未知名称、缺号和空段。
Unix核对dev/inode，Windows句柄不共享DELETE；可信父目录、OS及文件系统仍为前提。
全部段在重开和历史读取前后核对名称、长度与身份；每次追加核对根/头/活动段，轮换时
核对完整目录。其他进程绕过锁修改密封段不受运行中防篡改承诺保护，后续完整重放仍必须验证。

没有记录的创世目录可只有 `genesis`，这是唯一的无段状态。任何零字节或部分尾段均拒绝
恢复；不自动删除、修补或忽略。创建目录或首段中断可以留下需要检查的未完成目录。
完整新段已同步但确认丢失时，重放可包含该块；不把此类失败说成确定未提交。

prepare/selection只计算完整帧预算，不创建段。若当前段剩余空间不足，下一次commit
使用create_new创建下一个连续段；完整记录从不跨活动段。commit重复总字节、段数、
帧大小、当前文件身份和长度检查，并重复真实状态/授权执行后才写。
先write_all完整帧，再sync_all；新段发布还需同步目录（Unix），成功后才更新内存状态。
任何开始写入后的I/O失败均将store置为不可用，worker终止，无自动重试、truncate或回滚。
Windows保留明确的目录持久化/断电限制，不把进程故障注入当作真实断电验收。

## 重放、历史与现有恢复工具

重开在稳定根锁内，按连续段号生成有界读取流，复用原记录解码和真实授权执行。
每段捕获长度，并分别要求实际EOF；最终也检查整个逻辑EOF和目录不变。
每个物理段必须在完整记录帧末尾结束，禁止读取流把跨段切开的帧拼接后接受。
非末段只有在紧接的下一完整帧无法容纳时才允许结束；重放核对这一规范轮换规则，
提前轮换、跨段拆帧和空尾段均拒绝，不能用非规范布局改变段数预算。
重建状态在任何错误后丢弃，完整重放完成前不返回状态或已认证历史。
钱包历史使用同一已持锁逻辑流和原提交摘要核对，保留全部记录供真实收款识别。

原 `ZVPRCP01` 检查点、旧单文件备份、备份段和派生索引不扩展含义；活动账本请求这些
接口时明确拒绝，并保持可用的活动store状态。活动重开/核验与原本独立可信的
`check_checkpoint(height, app_hash)` 一起使用，后者仍不证明提供者披露了最新状态。
本阶段不导入快照、不剪枝、不提供活动归档迁移或增量备份。节点签名状态始终不属于账本恢复。

## 跨语言与网络约束

旧worker继续使用IPC第3代指纹。活动worker使用独立固定指纹
`ZEVUNE-POOL-IPC-4:zevune-orchard-lab-1:16:28134:selection-64:active-segments-1:1000000:1073741824`。
Go从独立固定的公开创世清单识别profile，在启动前完成有界清单检查并选择准确指纹、
高度限制及区块/选择编码；任何不匹配立即终止，无降级。请求/响应帧布局和真实权限不变。

上述不变指原有op0至op5：普通响应145字节，selection响应153字节。
仅IPC4增加op6（空请求payload）：同一持锁且available的store返回原145字节响应，追加
大端u64逻辑总字节（头+完整帧）、u32段数、u32当前尾段字节，总长度固定161。
普通拒绝仍是161字节、后16字节为零；只有status=0才解释容量。legacy客户端在发送前
拒绝此操作，legacy worker收到op6为协议错误终止。存储或身份异常仍是fatal，不返回成功快照。
Go按已pin清单推导的真实头长度检查字节下界（头+150×高度）、各profile上界和关系；
高度0要求无段且尾长0，有记录要求至少1段且尾长至少150，未知或不一致结果失败关闭。
容量是与该次committed Summary对应的快照，不是重新独立证明全部密封段未被外部篡改。

旧labnet配置Version1与AppVersion2继续只允许旧profile；活动网络使用配置Version2、
AppVersion3并绑定03清单。AppState及可信配置摘要继续绑定清单，所有网络/RPC/同步/
检查点/容量调用按已认证profile检查。旧配置不能夹带03清单，新配置不能夹带01/02清单。
公开ChainID继续沿用实验链标识，实际实例身份仍由独立pin的创世/配置决定。
同步对当前块结果的证明仍要求下一高度已签名头，不改变tip-1约束。

## 冻结验收

1. 正常worker/Go连续执行9999/10000/10001，选择、预演、最终执行、提交摘要一致；
   高度边界的真实非零付款、找零、重开继续10002、收款后再次花费及重复拒绝必须有证据。
2. 使用默认生产代码路径提交至少100000个区块、多次真实活动段轮换，重开后继续提交；
   记录总字节、段数和时间。100000空块约15MB，不作为64MiB或承诺容量越界证明。
3. 旧模式在10001仍拒绝；错清单/profile、混合IPC、错误网络配置均失败关闭；01/02回归保留。
4. 完整帧/恰好满段/再一帧轮换、最大合法块、总预算与段数边界；小容量故障测试只作补充。
5. 双进程锁、缺段/换段/改名/链接/截断/尾字节/重算校验和但无效授权；失败前后状态和字节。
6. 创建下一段、部分写入、同步失败、完整持久化但确认丢失故障；区分完整恢复和明确拒绝。
7. Ubuntu/Windows原生Rust/Go回归、真实钱包历史与付款、既有四节点回归保留。
   活动四节点启动/付款/重启应验证，但100000增长计数只来自正常worker/Go，不能冒称四节点共识100000块。

本阶段最终需冻结源码base/head/tree，独立代码审核、准确源码CI及缺陷修复完成后才验收。
原历史技术文档缺口保持；本设计沿用现有已实现LAB2 backend，不引入新密码学组件或验证后门。
